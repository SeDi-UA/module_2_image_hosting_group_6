# Image Hosting Application (Group 6)

Простий, швидкий та захищений веб-сервіс для завантаження, зберігання та перегляду зображень. Проєкт побудований на базі стандартної бібліотеки Python (без використання сторонніх веб-фреймворків) та оркеструється за допомогою Docker Compose з використанням Nginx як зворотного проксі-сервера (Reverse Proxy).

---

## 🛠 Технологічний стек
* **Backend:** Python 3.12 (чиста стандартна бібліотека `http.server` + `psycopg2-binary`)
* **Database:** PostgreSQL 16 (Alpine)
* **Web Server / Reverse Proxy:** Nginx 1.25 (Alpine)
* **Containerization:** Docker, Docker Compose (Multi-stage builds)
* **Frontend:** HTML5, CSS3, JavaScript (Vanilla JS)

---

## 🚀 Інструкція з розгортання та запуску

### Попередні вимоги
Переконайтеся, що на вашому комп'ютері встановлено та запущено **Docker Desktop**.

### Кроки для запуску:

1. **Клонуйте репозиторій** та перейдіть у папку проєкту:
   ```bash
   git clone <посилання_на_ваш_репозиторій>
   cd module_2_image_hosting_group_6
   ```

2. **Запустіть оркестрацію контейнерів:**
Побудуйте образи та підніміть сервіси однією командою:
    ```bash
    docker compose up --build
    ```

3. **Перевірте працездатність:**
Відкрийте браузер та перейдіть за адресою:
👉 http://localhost:8080/ (Веб-інтерфейс через парадні двері Nginx)

### Почистити дані БД (Rebuild з нуля):

Якщо потрібно повністю скинути базу даних та створити її наново:
```bash
    docker compose down -v
    docker compose up --build -d
```

## 🗄️ База даних та збереження даних

У проєкт інтегровано **PostgreSQL 18** для надійного збереження метаданих завантажених зображень.

### Метадані, що зберігаються в БД:
* id (використовується як первинний ключ).
* Унікальний системний UUID файлу.
* Оригінальне ім'я файлу (для збереження читабельності при перегляді).
* Розмір файлу та його MIME-тип.
* Дата та час завантаження (`created_at`).
* Тип (розширення) файлу.

Ініціалізація структури таблиць відбувається автоматично під час першого запуску PostgreSQL завдяки монтуванню `./config/init.sql` в `/docker-entrypoint-initdb.d/`.

## 🖥️ Опис ключових маршрутів API та логіки

Завдяки зв'язці Nginx + Python, навантаження розподілено оптимально:
* **Nginx (Порт 8080)**: миттєво самостійно роздає всю статику (`/static/*`) та збережені користувачами зображення (`/images/*`) без залучення Python.
* **PostgreSQL (Порт 5432)**: зберігає структуровані метадані та обробляє швидкі вибірки.
* **Python (Порт 8000)**: обробляє виключно динамічні запити та API, сховавшись за мережевим мостом Docker.

### Основні роути додатка:
* `GET /` — Головна сторінка.
* `GET /upload` — Сторінка форми завантаження нових файлів.
* `POST /upload` — API-ендпоінт для завантаження файлів та запису метаданих у БД.
* `GET /images` — Сторінка детального перегляду списку завантажених файлів.
* `GET /api/images?page=1&limit=10` — API-ендпоінт галереї з підтримкою **пагінації** (повертає JSON із метаданими зображень, загальною кількістю сторінок та елементів).

## 🔒 Валідація та безпека

У проєкті реалізовано надійну **двохрівневу систему валідації** для захисту сервера від завантаження шкідливих або пошкоджених файлів.

### 1. Клієнтська валідація (Frontend / Vanilla JS)
* **Миттєвий фідбек:** Скрипти валідують файли безпосередньо в браузері користувача перед відправкою на сервер.
* **Обмеження форматів:** Перевіряється розширення файлу (дозволено лише `.jpg`, `.jpeg`, `.png`, `.gif`).
* **Контроль розміру:** Файли, що перевищують **5 МБ**, блокуються на етапі вибору, запобігаючи марному витрачанню трафіку.

### 2. Серверна валідація (Backend / Python + Pillow)
Бекенд ніколи не довіряє клієнтським даним на 100% і проводить ретельну повторну перевірку:
* **Повторна перевірка типу та розміру:** Сервер дублює перевірку розширення та ліміту в 5 МБ на випадок прямого обходу форми через API-запити.
* **Глибока перевірка вмісту через Pillow:** Для перевірки того, що завантажений файл дійсно є справжнім і неушкодженим зображенням (а не просто перейменованим шкідливим скриптом `.exe` чи `.sh`), бекенд використовує бібліотеку **`Pillow`**. Спроба завантажити підроблений файл викликає помилку валідації зображення та відхиляється сервером.

### 3. Безпека середовища
* **Низькі привілеї (Non-root user):** Додаток усередині Docker працює від імені обмеженого користувача `appuser`. Навіть за умови виявлення вразливості, зловмисник не зможе отримати права root-користувача у контейнері.
* **Унікальність імен (UUID):** Кожне збережене зображення переіменовується в унікальний UUID. Це унеможливлює умисний або випадковий перезапис наявних файлів на сервері.
